Playbooks - Handoff note

Testing UX (testv2)

How we turned playbook testing from a one-shot sanity check into a real QA surface.

/component/canvas/testv2 · prototype/app/component/canvas/testv2/

The problem

A Playbook is automation that runs unattended on real customer email. Before a support manager flips it on, they have to trust it does the right thing across the messy variety of real inbound - the refund that is over policy, the group enquiry with dietary needs, the date that is sold out. "It looks right in the editor" is not that trust.

The testing UX we inherited did not earn it:

Before
  • Hardcoded inputs. One of four fixed mock tickets. No custom email, no real past conversation.
  • Throwaway. A run lived inside the editor mode and vanished on exit. No saved cases, no history.
  • No verdict. You eyeballed a trace. "Did it work?" was a judgement call every time.
  • No version awareness. Nothing tied a result to the playbook version, so "did my edit change this?" was unanswerable.
  • A mode bolted on, not a place you would actually do QA.
After (testv2)
  • Saved scenarios - custom email or a real past thread.
  • Run history per scenario, capped at 50.
  • Pass / fail / cancelled outcome on every run.
  • Version-hashed runs + run-to-run Compare.
  • A workspace with its own rail, footer, and live trace.

Net before: you could sanity-check one canned input, once. You could not build a regression suite, replay reality, or catch a change that broke a path that used to pass.

The solution: a scenario-based test workspace

1. Scenarios are saved, first-class objects

A Scenario is a named, persisted test case (localStorage, keyed hiver.playbooks.walkjapan.v1.testv2). You build a library of them; each carries its input and its own run history. Seeded with three Walk Japan cases. A scenario row shows its last-run status at rest, no hover needed: passing failing never run

2. Two ways to supply input, both real-feeling

  • Custom - compose a synthetic email (from, subject, body, labels). For edge cases you design deliberately.
  • From inbox - pick a real past conversation from a fixture mailbox (10 Walk Japan threads) through a searchable, filterable picker (free-text, date range, label chips). For the messy shape of actual inbound.

Switching modes warns before discarding the current input.

3. Run -> trace -> artifact

Run scenario -> chips animate on canvas -> trace fills -> per-step artifact -> pass / fail

Each step renders a chip-specific artifact in its own pane: a draft reply reads like a compose preview, an HTTP call as flush request / response lines, a note as an inline note, a tag as pills. Prose-first, no card chrome. The run ends with a clear outcome, not a trace you have to interpret.

4. Run history + version awareness

Every run is saved against its scenario with the versionHash of the playbook it ran against, the branch path it took, the outcome, and timing. This is what makes "which version produced this, and did my edit change it?" answerable.

5. Compare two runs

Pick two runs of the same scenario and diff them. The core regression question - did this edit change behaviour? - in one gesture.

Plus a Batch tab (UI shipped, runner stubbed in v1): select saved scenarios or filter the fixture mailbox, then run many at once. Progressive results table, branch coverage, and drill-down trace land in v2.1.

How it is structured

Test is a set of canvas modes, not a modal: test-idle, test-running, test-done, test-diff. The canvas becomes the live trace surface; the right rail carries the Scenarios / Batch tabs; the footer carries Run / Stop / Replay / Compare.

What is mocked or deferred

Read before trusting a result
  • Runs are simulated - plausible fakes from each action's declared output types. No real execution, no API calls.
  • Wait steps are skipped in test.
  • Batch runner is a stub - it alerts instead of running. v2.1.
  • The inbox is a fixture - 10 Walk Japan threads, not a live mailbox.
  • Persistence is localStorage only. No backend.

All intentional - this is a design prototype proving the testing model, not a working integration.
